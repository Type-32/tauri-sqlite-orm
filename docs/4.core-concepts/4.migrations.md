Migrations are the process of keeping your database schema synchronized with your application's schema definitions in code. This ORM provides a powerful migration system that can handle both simple and complex schema changes.

## How It Works: The Schema Signature

The `migrateIfDirty()` method relies on a **schema signature**.

1. It computes a unique string based on your current code schema (tables, columns, types, constraints).
2. It compares this signature to one stored in a special `_schema_meta` table in your database.
3. If the signatures don't match, the ORM considers the schema "dirty" and runs the non-destructive migration process.

## Migration Methods

You have three primary methods for managing migrations, each with a different purpose.

### `db.migrateIfDirty()`

This is the **recommended method for development and simple deployments**. It's an all-in-one, non-destructive command that:

1. Automatically checks if the schema is dirty using the signature comparison.
2. If dirty, it runs the migration logic to add any missing tables or columns.
3. After migrating, it updates the stored signature to match the new schema.
4. It returns a `Promise<boolean>` which resolves to `true` if a migration was performed.

This method will **never** delete tables or columns, making it safe to run on application startup.

```ts [src/startup.ts]
// Place this in your app's startup logic
await db.migrateIfDirty();
```

### `db.migrate(options?)`

This is the more powerful, underlying migration method. It directly compares your code schema with the database structure and applies changes. Crucially, it can be configured to perform **destructive actions**.

The method takes an optional `options` object:

- `options.performDestructiveActions: boolean` (default: `false`)

**Without options (Safe Mode):**

- `CREATE TABLE` for any new tables.
- `ALTER TABLE ... ADD COLUMN` for any new columns.

**With** \`{ performDestructiveActions: true }\` **(Destructive Mode):**

- Performs all actions from Safe Mode.
- `DROP TABLE` for any tables that exist in the database but not in your code schema.
- `DROP COLUMN` for any columns that exist on a table in the database but not in your code schema.

> [!warning]
> Destructive mode can lead to data loss. It is intended for controlled scenarios, such as resetting a development database or within carefully planned migration scripts. **Do not** run this on application startup in a production environment.

```ts [src/migrate.ts]
// Example: Safely add new columns/tables
await db.migrate();

// Example: Sync schema exactly, deleting any extra tables/columns
await db.migrate({ performDestructiveActions: true });
```

### `db.isSchemaDirty()`

This method checks the schema signature without performing any migrations. It's useful for UI feedback or custom logic. It returns: :br `Promise<{ dirty: boolean; current: string; stored: string | null }>`

## Important Limitations

Even with destructive actions enabled, the migrator **DOES NOT** support:

- **Renaming columns or tables.**
- **Altering a column's type or constraints** (e.g., changing `TEXT` to `INTEGER` or adding `UNIQUE` to an existing column).

For these operations, you must use the [Tauri SQLite ORM Provided Schema](../advanced-topics/manual-schema-management) within a custom script.
